SHAPE_HEADING_SIZE: what should a title's OWN size be?

SETTLED — 3 September 2026. Nothing on this page ships. The owner declined all three increases: the system app's page title and record heading stay at h2 (32px), and the client portal stays at h3 (24px). The reason is not a preference about size, it is that this is already somebody's own choice — the scale setting (compact / comfortable / large, shared/scale.ts) moves the root font size for the whole app, and because every size in the theme is rem, a title grows with it. Picking 44 here would be choosing for a person who can already choose. In the owner's words: “there's no need to increase the sizes anyway, because this setting has an option to make it small, comfortable, or large.”

That reasoning has a precondition, and it can rot. It holds only while headings are rem. A heading hand-set in px would sit still while every step of the scale control moved around it — the setting would look broken on exactly the text somebody reached for it to fix. The full argument, including that precondition, is recorded in shared/scale.ts, which is the file a reader will actually open.

What this does NOT settle, so nobody reads more into it than was decided: the kit's Title still stops at 32 with no 44 rung, while Headline draws 44 and 56 and is wired to nothing. That mismatch stays open upstream. The ruling is that we are not spending the app's headings to fix it — not that it is fixed. The comparison below is kept in full, unedited, because a decision whose options were deleted cannot be re-examined.

The client's reference PDF names three roles: display-m (56px) = “Page title”, h1 (44px) = “Record heading”, h2 (32px) = “Section title”. Every screen built through MainScreen / RecordChrome renders its title through SHAPE_HEADING_SIZE, which only ever offers h2 or h3 — there is no wired path to 44 or 56 at all, on either door.

Structural catch, not just a number swap: the component both templates render through, Title (shared/ui/components/title/title.tsx), is documented in its own file header as the kit's “Section header” (chapter 13's Section-header specimen) and its size ladder is only ever defined as h2 / h3 / h4 — there is no h1 or display-m variant on this component to widen into. The kit's OWN 44px “page's own name” step already exists, on a different component (Headline, in shared/ui/components/typography/typography.tsx), but nothing in MainScreen or RecordChrome wires a page title to it. So the open question is not “which value does SHAPE_HEADING_SIZE return” — it's whether a page/record title should keep running through the section-header primitive at all, capped at 32, or move to the page-name primitive the kit already drew for this and left unplumbed.

What this page does not settle

  • Whether the fix is data-only (widen SHAPE_HEADING_SIZE's Record<ScreenDensity, ...> return type) or structural (retire Title from the page/record-title role entirely and wire MainScreen/RecordChrome to Headline instead, leaving Title for actual in-page section headers, which is what its own file header says it is).
  • Whether comfortable (system app) should land on h1 or display-m — the reference calls display-m “Page title” and h1 “Record heading,” which argues for MainScreen at display-m and RecordChrome at h1 rather than one shared step for both.
  • Whether calm (portal) should match comfortable's new step exactly, or keep one step below it the way it does today (h3 vs h2) — the portal's narrower 60rem column has more headroom per line than the full-width system app does.
  • This is vendored, hash-checked code (shared/ui/, Law R45/R46 in this repo's CLAUDE.md, hash pinned in shared/ui/VERSION.json at tag v1.2.13 of Kwapso/kwapso-ui-ux). Nothing here should be hand-patched in this repo — the fix belongs upstream, and Alaap owns that swap per the design-kit pipeline.
